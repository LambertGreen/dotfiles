*** TODO Add direnv integration to Neovim (editor parity for project-local tools)
**** Context
Policy (=docs/PACKAGE_POLICY.md=) is *prefer project-local tools over global*,
with =direnv= as the mechanism: entering a project puts its tools first on
=PATH=, so shells, editors and AI agents all resolve the right version without
having to know anything about it.

Emacs already honours this via =envrc-global-mode=
(=configs/emacs_common/dot-emacs.d/config/init-utils.el=). *Neovim does not* —
no direnv integration was found in =configs/nvim_common/dot-config/nvim/=.

So today Emacs and Neovim disagree about the same project: Emacs picks up the
project's =black= / =pyright= / etc., Neovim silently falls back to whatever is
global. That is the exact silent version-skew the policy exists to prevent.

Verified working on the Emacs side: an agent shell in this repo resolves
=python3= and =pytest= to =.direnv/python-3.13/bin/=, not Homebrew.
**** Action Items
1. Add a direnv plugin to the =nvim= config (e.g. =direnv.vim= / =direnv.nvim=),
   or have nvim inherit the environment the way =envrc= does per-buffer.
2. Verify parity: in a project with a pinned formatter/LSP, confirm Emacs and
   Neovim resolve the *same* binary.
3. Confirm LSP servers launched by nvim inherit the project =PATH= (this is the
   case that actually matters — name-based resolution like
   ="pyright-langserver"= only works if =PATH= is right).
4. Do NOT wire format-on-save to a global fallback formatter — see the
   formatter caution in =docs/PACKAGE_POLICY.md=.
**** Notes
To be picked up via =~/dev/my/ai= (Cortana), which carries the broader
cross-project context. As of 2026-08-31 that workspace *is* bootstrapped on this

*** DONE Fix Pacman command execution on Windows
CLOSED: [2025-12-26 Thu]
**** Problem
Pacman commands failed with "The syntax of the command is incorrect" when running from PowerShell.
**** Root Cause
The execution chain was too complex: Python → spawn_wt_clean.bat → wt.exe → pwsh.exe → run_tracked.ps1 → cmd.exe → msys2_shell.cmd → bash → pacman. PowerShell's parameter parsing mangled the quoted command strings.
**** Solution
1. Modified WindowsTerminalExecutor to detect MSYS2 commands (pacman) and route them through bash.exe + run_tracked.sh instead of PowerShell + run_tracked.ps1
2. Created wrapper batch file to set DOTFILES_NO_EXEC_ZSH=1 before launching bash (prevents .bash_profile from exec'ing to zsh)
3. Added DOTFILES_NO_EXEC_ZSH guard to dot-bashrc and dot-bash_profile
4. Simplified pacman.py to return raw pacman commands (terminal executor handles MSYS2 wrapping)
**** New execution chain
Python → spawn_wt_clean.bat → wt.exe → cmd.exe /c wrapper.bat → bash.exe -l script.sh → run_tracked.sh → pacman
