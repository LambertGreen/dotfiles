# Two axes, kept separate on purpose:
#   Open / Completed  — workflow STATE, expressed by the outline + TODO keyword
#   :design: / :bug:  — what the item IS, expressed by tags
#
# Tags rather than TODO keywords because an Org item may hold exactly ONE todo
# keyword. Making BUG a keyword would cost the STRT/WAIT/HOLD vocabulary for
# precisely the items most likely to need it. A second sequence
# (#+TODO: BUG | FIXED) would earn that cost only if bugs had a genuinely
# different lifecycle here; they don't — found, worked, done, same as the rest.
# Follows the split already in init-org.el, where (sequence ...) carries
# workflow and (type PROJ IDEA) carries kind.
#
#   :design:  deliberate project-level work — a decision to make or a
#             capability to add. Often ends as a record in ai/retros/decisions/.
#   :bug:     defect found through usage; the system did something other than
#             what it claims. Usually traceable to a retro under
#             ai/retros/dotfiles-maintenance/.

*** TODO =sudo_helper.py= cannot be imported on Python 3.9              :bug:
**** Context
=src/dotfiles_pm/sudo_helper.py:64= declares =def _find_linux_askpass() -> str | None:=

- Add =from __future__ import annotations= (one line, restores 3.9 import), or
- Use =Optional[str]=, or
- Decide 3.10+ is the floor and *declare* it (nothing in the repo states a
  minimum today, which is why this went unnoticed).

*** TODO =emacs-mac-exp@31= breaks when a dependency's dylib bumps      :design:
**** What happened (2026-09-01)
=just upgrade= bumped =tree-sitter= 0.26.13 → 0.27.0, replacing
=libtree-sitter.0.26.dylib=. =emacs-mac-exp@31= is a =--HEAD= build linked
against =.0.26=, so =emacs --version= died with a dyld "Library not loaded".
Routine package maintenance took out the primary editor.
**** Why it recurs
=upgrade-emacs-mac-exp.sh= guards the *forward* case — upgrading Emacs and
finding the new build broken. Nothing guards the *reverse*: upgrading a
**dependency** out from under a HEAD-built Emacs. Same fragility, from the side
nobody instrumented. Any brew upgrade touching tree-sitter, jansson, gnutls,
libgccjit… can do this again.
**** Recovery that worked (keep this — it is not obvious)
=just upgrade-emacs-mac-exp= did *not* help: advancing to the current HEAD
(=ecf4b0e=) fails to build because the tap's =emacs-mac-31.1-multi-tty.diff= no
longer applies (=src/frame.c= hunk rejected). The fix is to rebuild the *same*
commit against the new dependency, using the formula's revision pin:
#+begin_src sh
HOMEBREW_EMACS_MAC_31_REVISION=<full-sha> \
HOMEBREW_NO_INSTALL_CLEANUP=1 \
  arch -arm64 brew reinstall --build-from-source \
  pkryger/emacsmacport-exp/emacs-mac-exp@31
#+end_src
Recover =<full-sha>= from =INSTALL_RECEIPT.json= in the current keg, or
=git -C ~/Library/Caches/Homebrew/emacs-mac-exp@31--git rev-parse <short>=.
**** Options to stop it recurring
- Teach =upgrade-emacs-mac-exp.sh= a =--rebuild-current= mode that pins
  =HOMEBREW_EMACS_MAC_31_REVISION= to the installed keg's SHA — the exact
  recovery above, as a first-class recipe
- Have =just upgrade= smoke-test Emacs afterwards and rebuild automatically if
  it stops launching
- =brew pin tree-sitter= (blunt: freezes it for neovim too)
**** Related
Detection is now covered — =doctor-check-health= runs the binaries rather than
just locating them (=e5634cf=). This item is about *prevention/recovery*.

*** DONE Elpaca source dirs stale after naming-scheme change            :bug:
CLOSED: [2026-09-02 Wed 13:17]
**** Symptom
Emacs started but the config aborted with a =*Warnings*= buffer:
#+begin_example
Non-existant source dir: "/Users/lgreen/.emacs.d/elpaca/elpaca/sources/emacs-popon/"
#+end_example
**** Cause
Not corruption. Elpaca changed how it names source directories: it now derives
the name from the recipe's =:repo= rather than the package name. Directories
cloned under the old scheme no longer match, so elpaca looks for
=sources/emacs-popon/= and finds only =sources/popon/=.

The rule is in =elpaca-git-repo-dir= (=elpaca-git.el=): repo basename with a
trailing =.el= stripped, and =name.hostname.user= when two packages collide.
**** Fix
Rename the affected dirs — no re-clone needed. Only three were genuinely wrong:
| =popon=          | → =emacs-popon=          |
| =eat=            | → =emacs-eat=            |
| =corfu-terminal= | → =emacs-corfu-terminal= |
**** How to diagnose it next time (the useful part)
Do **not** infer the expected name from the on-disk git remote. That is wrong
often enough to bite: =pinentry='s clone has remote =pinentry-el=, but its
recipe is =emacsmirror/pinentry=, so elpaca wants =sources/pinentry=. Renaming
it "correctly" broke it.

Ask elpaca instead — it computes the answer itself, and this reports the exact
set in seconds:
#+begin_src sh
emacs --batch -l ~/.emacs.d/init.el --eval '(let (missing)
  (dolist (cell (elpaca--queued))
    (let* ((e (cdr cell))
           (dir (ignore-errors (elpaca<-source-dir e))))
      (when (and dir (not (file-exists-p dir)))
        (push (format "%-22s wants %s" (elpaca<-package e)
                      (file-name-nondirectory (directory-file-name dir)))
              missing))))
  (princ (format "MISSING: %d\n" (length missing)))
  (dolist (m (delete-dups missing)) (princ (concat "  " m "\n"))))'
#+end_src
A crude scan comparing directory names to git remotes flagged **34** candidates;
elpaca's own computation found the real answer. Verify with a full
=emacs --batch -l init.el= plus =(elpaca-process-queues)= — exit 0 and no
=Elpaca error= lines means clean.
**** Note
Wiping =elpaca/= also fixes this, and is the usual reflex — but it re-clones all
204 packages (515 MB) to solve a three-directory naming problem.
=elpaca/= is gitignored inside the =dot-emacs.d= submodule, so nothing here is
tracked either way.
